# SurrealDB Migration Plan: JMMinistry

This document outlines the step-by-step strategy to transition the JMMinistry application from PostgreSQL/EF Core to SurrealDB.

## Phase 1: Infrastructure & Data Modeling
1.  **SurrealDB & MinIO Setup:** Update `docker-compose.yml` to include SurrealDB and MinIO services with persistent volumes.
2.  **Secret Management:** Define shared keys for JWT (API/SurrealDB) and S3 credentials (API/MinIO).
3.  **Schema Application (SurrealKit):** 
    - Initialize `surrealkit` in the `/database` directory.
    - Organize schema into `schemas/`, `events/`, and `functions/`.
    - Use `surrealkit sync` for declarative development updates.
4.  **Identity Strategy:** Ensure all `user` records use explicit IDs (e.g., `user:123456789`) matching the person's document.
5.  **Role Migration:** Initialize the `role` table and migrate user-role assignments using `member_of` edges.

## Phase 2: .NET API Refactoring
1.  **SurrealDB Client Integration:** Add `SurrealDb.Net` NuGet package.
2.  **MinIO (Presigned URL) Integration:** 
    - Implement a `GetUploadUrl` endpoint that generates MinIO presigned URLs.
    - The client will upload directly to MinIO and pass the object path back to the API.
    - Remove server-side file stream handling from the `IPhotoService`.
3.  **Incremental DTO Refactoring:** 
    - As each handler is refactored, move its required DTOs/Enums from `JMMinistry.Common` to `JMMinistry.Application` or a feature-specific namespace.
4.  **Authentication Middleware:**
    - Replace Microsoft Identity with JWT Bearer validation against SurrealDB Scopes.

## Phase 3: Business Logic Transition
1.  **Move Recursive Logic:** Replace C# recursive methods and PostgreSQL CTEs with SurrealQL graph paths (e.g., `->(leads->cell)*`).
2.  **Automation Events:** Rely on SurrealDB `DEFINE EVENT` for spouse symmetry and co-leadership sync, removing this logic from C# handlers.

## Phase 4: Validation & Testing
1.  **Unit Tests:** Update existing tests to use a SurrealDB test container.
2.  **Integration Tests:** Verify complex graph traversals for hierarchy and permissions.
3.  **Performance Tuning:** Define indexes on traversal fields if necessary.

## Phase 5: UI & Frontend
1.  **Update JWT Handling:** Ensure the frontend correctly stores and sends the SurrealDB-generated token.
2.  **Role-Based UI:** Update access checks to read from the `roles` array in the SurrealDB token claims.

## Phase 6: Codebase Cleanup
1.  **Shared Project Refactoring:**
    -   Assess `JMMinistry.Common` usage.
    -   Move necessary DTOs and Enums (e.g., `UserInfoDto`, `MaritalStatus`) into `JMMinistry.Application` or a new `JMMinistry.Contracts` library.
    -   Delete `UIStrings` and other Blazor-specific resources.
    -   Remove `FluentValidation` base classes if no longer shared across projects.
2.  **Unused Feature Removal:**
    -   Scan `Features/` folder for logic previously tied to the Blazor frontend.
    -   Remove any EF Core specific extensions or "Ghost" code from the migration.
3.  **Project Deletion:** Delete the `JMMinistry.Common` project once empty.
4.  **Database Migration Cleanup:** Delete the `Migrations/` folder in the Persistence project and all PostgreSQL-specific SQL files.

---

## Technical Constraints & Decisions
-   **Blob Storage:** Replaced local file management with **MinIO**. The .NET API will provide presigned URLs, and the Flutter client will upload directly to MinIO.
-   **Identity Compatibility:** Confirmed. The Flutter client will use the JWT tokens generated by SurrealDB scopes, which are aligned with standard claim types.
-   **Identity Strategy:** User record IDs must be explicit document numbers (e.g., `user:123456789`) for consistency.
-   **Schema Management:** Using **SurrealKit** for declarative schema synchronization and controlled production rollouts.
